# UI·서비스 기획 담당 협업 가이드

## 역할 경계

| 담당 | 책임 | UI 담당이 합의할 내용 |
|---|---|---|
| 1. 백엔드·통합 | API, 파이프라인, 오류·상태·점수 계산 | 입력 필드, 응답 JSON, 시간 제한, 부분 실패 |
| 2. 특허 데이터·RAG | KIPRIS 수집, 정제, 검색, 인용 검증 | 문헌 제목·원문 구절·구획·출처·불확실성 |
| 3. 시장조사·평가 | 시장 근거 품질, 출처·발행일, 평가 사례 | 사실/가설 구분, 미확인 사유, 다음 검증 |
| 4. UI·시나리오·발표 | 입력·결과 화면, 사용자 흐름, 시연·사용 안내 | 사용자가 판단할 정보와 읽는 순서 |

본 문서는 역할표를 해석한 협업 제안이다. 특정 파일의 소유자나 팀원의 배정은
Git 이력만으로 확정하지 않으며, 역할 변경은 팀과 합의한다.

## 무엇을 어디에 올리는가

| 내용 | 위치 | 공유 방법 |
|---|---|---|
| 새 기능·서비스 아이디어 | GitHub Issues → 작업·기능 요청 | 제목에 `[제안]`, 관련 영역 frontend·문서 선택 |
| 화면 오류·사용 불편 | GitHub Issues → 버그 | 재현 순서·기대 결과·화면 첨부 |
| 확정 전 화면·분석 방향 | `docs/` 제안 문서 | 제안 상태를 표시하고 PR로 검토 |
| 화면 구현 | `frontend/` | 본인 feature 브랜치 → develop PR |
| 시연 시나리오·실행법 | `docs/ui-guide.md` | 구현과 함께 갱신 |
| 논문·서비스·참고 링크 | 디스코드 storage / 노션 자료실 | 적용할 아이디어는 관련 GitHub 이슈에 요약·연결 |
| API 변경 요청 | GitHub 이슈 + `docs/api_contract.md` | 1번 담당자와 합의 후 수정 |

참고 링크는 주소와 함께 '왜 참고하는지', '어떤 화면·작업에 적용할지',
'확인한 기능과 추정한 구현의 차이'를 적는다. 타사 서비스 내부 구현을 확인한 것으로 단정하지 않는다.

## 제안 이슈 작성 예시

제목: `[제안] 경영진 요약과 R&D 근거 화면 분리`

- 사용자 문제: 요약과 원문 근거가 섞여 핵심 판단과 세부 확인이 어렵다.
- 제안: 요약 / 상세 근거 / 다음 검증 탭으로 나눈다.
- 기대 효과: 의사결정자는 핵심을, 연구자는 인용과 한계를 확인한다.
- 필요 데이터: 원문 구절, 출처 링크, 분석 상태, 미확인 사항.
- 협의 대상: 1번 응답 형식, 2·3번 근거 필드.
- 완료 기준: 샘플 제출·빈 입력·결과 초기화·다운로드가 작동하고 시연 표시가 유지된다.
- 상태: 제안이며 팀 승인 전 확정 요구사항이 아니다.

## 서비스 아이디어 후보 (미확정)

1. **근거 카드**: 출처·발행일·원문 위치·주장을 함께 보여준다.
2. **확인 수준 분리**: 확인된 사실, 사용자 주장, AI 가설, 미확인 항목을 구분한다.
3. **다음 검증 체크리스트**: 근거 부족을 막연한 낮은 점수 대신 다음 조사로 연결한다.
4. **기업 비교**: 두 기업의 같은 기술 과제를 동일 항목으로 비교한다. 현재 아이디어 입력 모델 확장이 필요하다.
5. **보고서 공유**: 입력 범위와 기준일, 근거 링크를 포함한 다운로드를 제공한다.

이번 시연은 1~3번의 화면 방향과 다운로드 흐름을 보여주는 첫 단계다.
실제 근거 검증·기업 비교·AI 분석이 구현됐다는 뜻은 아니다.

## 본인 작업 순서

최신 develop 받기 → 작은 작업 이슈 정의 → feature 브랜치 → 로컬 수정·검증
→ README·사용법 갱신 → 작업별 커밋 → 최종 검증 후 푸시 → develop 대상 PR.

API 담당자에게는 먼저 다음을 확인한다.

- 입력은 아이디어 중심인지 기업 비교 중심인지?
- 응답의 특허/시장 결과가 모두 있어야 하는지, 일부만 반환할 수 있는지?
- 검색 결과 없음·타임아웃·출처 없음 상태를 어떻게 구분하는지?
- 점수를 제공한다면 계산 기준과 사용자에게 설명할 한계는 무엇인지?
