# IdeaLens 프로젝트 목표·PR 분석 안내서

> 프로젝트 목표의 단일 기준 문서다. 각 항목은 도달할 목표 상태이며 구현 여부는 적지 않는다(현재 구현 상태는 PR 분석의 영역 요약 카드를 따른다). README의 '구현 방향'은 이 문서의 요약이다.
> PR 자동 분석(scripts/review)은 분석기 종류와 관계없이 이 문서를 지시문에 붙여 목표 연결·역할·규칙을 판단한다. 인용은 PR이 직접 다루는 세부 단계 ID를 대표로 쓰고, 개별 ID로 최대 6개까지 쓴다(예: 특허 수집 PR → 대표 B-PAT-2, 함께 B-GOAL-1).
> ID 묶음: GOAL 상위 목표 · EVID 근거 원칙 · PAT 특허 · MKT 시장 · INT 통합 · EVAL 평가 · PRIO 우선순위 · SCOPE 범위 · MOD 담당 영역 · RULE 팀 규칙(AGENTS는 저장소의 AGENTS.md).
> 항목 상태는 [확정] [초안] [비어 있음]으로 표기하고 리더가 확정한다. [초안] 항목을 근거로 쓸 때는 "초안 기준"임을 밝히고, [비어 있음] 항목은 근거로 쓰지 않고 판단을 보류한다. 편집 규칙: ID는 영문 대문자 묶음과 번호 하나로 쓰고, ID 바로 뒤에 한 칸 띄워 상태를 적어야 자동으로 읽힌다.

## 목표
- B-GOAL-0 [초안] 개발 기반: CI, Docker 개발 환경, PR 협업 자동화(리뷰어 지정·PR 분석·Notion 기록·영역 요약 카드)를 안정적으로 유지한다.
- B-GOAL-1 [초안] 특허 근거: 아이디어의 기술 구성과 관련된 국내 특허·실용신안을 KIPRIS Plus에서 수집·정제·색인·검색하고, 인용이 검증된 특허 분석 결과(PatentReport)를 만든다.
- B-GOAL-2 [초안] 시장 근거: 수요·경쟁/대체재·가격·구매자·도입장벽 5개 차원별 시장 근거를 수집·정제·색인·검색하고, 차원별 판정과 인용이 검증된 시장 분석 결과(MarketReport)를 만든다.
- B-GOAL-3 [초안] 통합 보고서·화면: 아이디어 구조화 결과를 특허·시장에 함께 넘기고, 두 결과를 검토 질문별로 연결해 경영진 요약·R&D 상세 보고서·미확인 사항·다음 검증 과제를 제공한다.
- B-GOAL-4 [초안] 평가: 특허·시장 각각 같은 지표로 검색 품질과 답변 품질을 재고, 같은 문항으로 일반 LLM 단독 응답과 RAG 응답을 비교한다.
- B-GOAL-5 [초안] 로컬 시연: 시연은 로컬 PC에서 Streamlit UI로 한다. 색인은 별도 DB 서버 없이 내장형 로컬 Chroma를 쓰고, 수집·색인 작업은 Docker Desktop의 app 컨테이너에서 하며, 결과는 호스트 `data/patents/chroma/`·`data/market/chroma/`에 저장한다.

## 근거 원칙
- B-EVID-1 [초안] 모든 사실 문장은 출처 ID·원문 위치·링크·시점과 연결하고, 출처에 없는 수치를 만들지 않는다.
- B-EVID-2 [초안] 사실·해석·가설·미확인을 구분하고, 근거가 부족하면 판단을 보류한다. 최종 판단은 사용자가 한다.
- B-EVID-3 [초안] 뉴스·기업 자료는 사업 신호이며 고객이 살 의사의 직접 증거가 아니다. 특허와 시장 자료의 글이 비슷하다는 점수만으로 관련 있다고 판정하지 않는다.

## 특허 파이프라인 (B-GOAL-1)
- B-PAT-1 [초안] 검색어 계획: 아이디어의 기술·문제·차별점에서 기술 요소 2~5개와 요소별 한국어·영어 검색어를 만들고, 그 계획으로 수집과 검색을 실행한다.
- B-PAT-2 [초안] 수집: KIPRIS Plus에서 서지·요약을 수집하고, 분석할 문헌은 청구항 상세(상품 이용 승인 범위)와 원문 링크를 가져온다. 출원번호로 중복을 없애고 새 자료만 더하며(증분), 원본 응답은 `data/patents/raw/`에 보관한다.
- B-PAT-3 [초안] 정제·청킹: `PatentDocument`·`PatentChunk`로 바꾸고 검색 단위로 나누며(청킹, 청구항은 1항 1청크), 요약·청구항 구획과 청구항 번호·유형(독립·종속)·상위항 참조·버전을 보존한다. 원문에 없는 번호는 추측하지 않는다.
- B-PAT-4 [초안] 색인·검색: `text-embedding-3-small` 임베딩을 로컬 Chroma `patents` 컬렉션에 증분 색인한다. 검색은 공통 검색 엔진(`src/retrieval/engine.py`)에서 dense(뜻 기반)·BM25(단어 일치)·hybrid(두 순위 결합) 중 고르고, 같은 문헌은 한 번만 반환한다.
- B-PAT-5 [초안] 분석·인용 검증: 서비스 진입점(`analyze_patents`)이 검색 결과로 `PatentReport`(문헌 최대 5건)를 만들고, 인용 근거별 유사점·차이점·미확인을 비교하며 인용이 해당 특허 원문 구획과 일치하는지 검증한다. 청구항 조회가 비거나 실패하면 청구항을 만들지 않고 초록 근거와 미확인으로 남긴다. 법적 특허성·신규성·침해 여부는 판정하지 않는다.

## 시장 파이프라인 (B-GOAL-2)
- B-MKT-1 [초안] 수집: `configs/technology_areas.yaml`의 공통·분야별 시장 키워드로 NAVER 뉴스의 제목·요약·링크·발행일을 모은다. DART 공시는 선택 출처다.
- B-MKT-2 [초안] 정제·중복 제거: 같은 URL을 합치고 제목 유사도 0.8 초과·발행일 3일 이내 기사를 한 중복 그룹으로 묶어 대표 1건을 `MarketDocument`로 남긴다.
- B-MKT-3 [초안] 색인·차원별 검색: 아이디어 5개 항목으로 차원별 질의를 만들고, 아이디어·출처 유형·발행일 필터와 공통 검색 엔진으로 차원별 근거 Top-5를 고른다(중복 그룹당 1건).
- B-MKT-4 [초안] 차원별 판정: 검색 결과마다 관련 여부를 판정해 관련 근거 수로 차원별 충분성을 정하고(검색 거리는 충분성 기준으로 쓰지 않음), 근거 성격(사업 신호·직접 수요)으로 확인됨·신호만 확인·미확인을 판정한다. 근거가 부족하거나 기대는 아이디어 항목이 모름이면 미확인으로 두고 검증 과제 1개를 낸다(실시간 보충 검색은 선택).
- B-MKT-5 [초안] 분석·인용 검증: 차원별 최대 3문장으로 `MarketReport`를 만들고, 사실 문장마다 인용을 달아 인용 존재·원문 일치·수치 출처·기준연도를 검증한다. 실패하면 최대 2회 다시 만들고, 그래도 실패한 문장은 빼고 해당 차원을 미확인으로 표시한다.

## 통합 (B-GOAL-3)
- B-INT-1 [초안] 공통 입력: 아이디어 한 문장을 문제·기술·고객·차별점·수익모델로 나누고(빈 항목은 최대 2회 재질문, 남으면 모름), 특허·시장 검색 요청으로 함께 바꾼다.
- B-INT-2 [초안] 결과 계약: 특허·시장 결과는 `src/schemas.py`의 `PatentReport`·`MarketReport`로 주고받고, 서비스 진입점(`src/services/`)과 분석 흐름(`src/pipeline.py`)이 두 결과를 모은다. Streamlit은 서비스 진입점을 직접 부를 수 있고 FastAPI(`src/main.py`)는 선택이다. 응답 계약은 `docs/api_contract.md`에 적는다.
- B-INT-3 [초안] 질문별 연결: 검토 질문마다 시장(M:)·특허(P:) 근거 번호를 사용 맥락·과제·구성·성능·도입 제약·근거 범위 6개 기준으로 연결하고, 한쪽 근거가 없으면 통합 판단을 보류한다.
- B-INT-4 [초안] 보고서·화면: Streamlit UI의 아이디어 입력 → 구성·검토 질문 → 근거·연결 검토 → 종합 보고서 4단계에 실제 결과를 보여 주고, 가상 시연 자료를 실제 결과로 표시하지 않는다.
- B-INT-5 [초안] 구현 비용: 사용자가 입력하는 구현 비용표(항목·소계)는 보고서의 보조 자료이며 사업성 점수나 판단이 아니다.

## 평가 (B-GOAL-4)
- B-EVAL-1 [초안] 검색 평가: 특허·시장 각각 평가 아이디어(`data/samples/ideas.json`) 기준 문항과 정답 자료 표시(`source_id` 라벨)로 Hit@5·Recall@5·Precision@5·MRR·nDCG@5와 응답 시간을 dense·BM25·hybrid별로 `evaluation/results/`에 기록한다.
- B-EVAL-2 [초안] 판정·답변 평가: 관련성 판정의 사람 라벨 대비 정확도·정밀도·kappa, 답변의 인용 정확성·근거 충실성·정확성과 오류 유형을 기록하고, 같은 문항으로 LLM 단독 응답과 RAG 응답을 비교한다.
- B-EVAL-3 [초안] 수치 보고: 평가셋·원문·색인이 준비되지 않은 영역은 품질 수치를 보고하지 않는다. 검색 방식을 비교할 때는 dense·BM25·hybrid 상위 결과를 모두 라벨 후보에 넣고, 설정·데이터 버전을 고정해 다시 잰다.

## 이번 시기 우선순위
> 우선순위는 작업 순서다. 목표·단계 항목에 연결되면 우선순위 밖 작업도 목표에 맞는 작업이다.
- B-PRIO-1 [초안] 특허 실데이터 확보: 청구항 상세 API 이용 승인을 확인하고, 평가 아이디어 기준으로 실제 특허를 수집·색인하며, 특허 평가셋으로 첫 검색 평가 수치를 낸다(B-PAT-2·B-PAT-3·B-PAT-4·B-EVAL-1).
- B-PRIO-2 [초안] 분석 생성: 시장 차원별 판정·분석 생성과 인용 검증으로 스키마 검증을 통과하는 `MarketReport`를 실제 데이터로 만들고, 특허 분석(`PatentReport`)도 실제 데이터로 확인한다(B-MKT-4·B-MKT-5·B-PAT-5).
- B-PRIO-3 [초안] 로컬 통합 시연: 서비스 진입점과 분석 흐름으로 두 결과를 UI의 근거·연결 검토와 종합 보고서 단계에 실제로 잇는다(B-INT-2·B-INT-3·B-INT-4·B-GOAL-5).

## 범위
- B-SCOPE-1 [초안] 자료 출처: KIPRIS Plus, NAVER 뉴스 검색 API, DART OpenAPI, 공공기관·연구기관·기업의 공식 자료. NAVER 뉴스는 교육 목적으로 쓰고 프로젝트 종료 때 폐기한다.
- B-SCOPE-2 [초안] 데이터 보관: 수집 원본·가공 데이터·색인·생성 보고서는 로컬에만 두고 Git에 올리지 않는다. 평가 문항·정답 라벨(`evaluation/`)은 Git으로 관리한다.
- B-SCOPE-3 [초안] 처리 흐름: 아이디어 구조화 → 특허·시장 수집·정제 → 색인·검색 → 판정·분석 생성 → 인용 검증 → 질문별 연결 → 보고서 → 평가.
- B-SCOPE-4 [초안] 향후 검토(목표 방향에는 맞지만 이번 시기 구현 대상이 아니며 순서는 리더가 정한다): 사내자료 연계, 특허 대표도면·이미지 분석(#27), DART 사업보고서 표 구조 보존·OCR(#29).
- B-SCOPE-5 [초안] 범위 밖(프로젝트 목표와 맞지 않음): 외부 호스팅(예: Streamlit Community Cloud)·클라우드 DB(예: Neon, Chroma Cloud) 연동이나 배포, 별도 Chroma 서버로의 전환, 근거 유무와 관계없이 사업성·수요·특허 위험을 하나의 점수·등급으로 매기는 기능, 특허성·침해 여부의 법적 판정. 자료 수집·생성을 위한 외부 API(KIPRIS·NAVER·DART·OpenAI) 호출은 범위 안이다.

## 담당 영역과 약속
- B-MOD-1 [초안] 공통 데이터 계약은 `src/schemas.py`(StructuredIdea, PatentReport, Market* 모델)와 공통 검색 계약 `src/retrieval/schemas.py`(SearchDocument, RetrievalResult)다. 계약 변경은 사용하는 영역 전체에 영향을 준다.
- B-MOD-2 [초안] 서비스 구조: 사용자 → `frontend/`(Streamlit UI) → `src/services/` → `src/pipeline.py` → `src/ingestion/`·`src/retrieval/`·`src/generation/`. `src/main.py`(FastAPI)는 선택 경로이고, 특허·시장 검색은 `src/retrieval/engine.py` 공통 엔진을 거친다.
- B-MOD-3 [초안] 비밀값(API 키)은 `.env`에만 두고 `.env.example`에는 이름만 둔다.
