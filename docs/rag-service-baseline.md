# IdeaLens RAG 서비스 현황 기준선

## 조사 범위와 판정

이 문서는 저장소 코드·문서와 현재 개발 환경에서 확인한 상태를 기록한다. 목표 문서나 README의 설명만으로 실행 완료를 판정하지 않는다. 비밀값은 확인·기록하지 않는다.

| 확인 구분 | 현재 확인 내용 |
|---|---|
| 코드에서 확인 | 특허·시장 수집, 전처리, 색인, dense/BM25/hybrid 검색, 관련성 판정, 구조화 분석, 통합 보고서 흐름이 구현되어 있음 |
| 문서에서 확인 | `docs/review-baseline.md`의 목표·이번 시기 우선순위는 `[초안]`; 출시 승인 기준으로 확정된 V1.0 게이트 문서나 운영 승인 기록은 확인하지 못함 |
| 현재 환경에서 확인 | 로컬 특허 처리 문서 28건, 로컬 특허 Chroma 246개 임베딩, 특허 raw 파일 357개; 로컬 시장 처리 파일 0건 및 시장 Chroma 0개; 특허 평가 후보 70건은 모두 미판정 |
| 연결 확인 | 이 환경의 설정된 공용 Chroma 연결 점검이 실패함. 시장 색인은 실행 불가, 특허는 KIPRIS 검색만 가능한 상태로 보고됨. 이 결과는 이 개발 환경의 점검이며 운영 환경의 상태를 뜻하지 않음 |
| 별도 확인 필요 | KIPRIS·OpenAI·NAVER·DART의 현재 권한·쿼터·비용, 운영용 Chroma와 배포 앱의 실제 상태, 복구·롤백 훈련 결과 |
| 정책 결정 필요 | `docs/review-baseline.md`는 외부 호스팅과 공용 DB를 범위 밖으로 적지만, README와 배포 문서는 Streamlit Community Cloud와 공용 Chroma를 실제 운영 경로로 설명함. V1.0의 배포·데이터 보관 범위를 한 기준으로 확정해야 함 |

### V1.0 출시 판단

**현재 확인 가능한 증거만으로 V1.0 완료를 선언할 수 없다.** 저장소에서 V1.0 태그·릴리스와 확정된 출시 체크리스트를 찾지 못했다. 특허 검색 라벨은 아직 비어 있고, 이 환경에서는 시장 색인이 없으며 공용 Chroma 연결도 실패했다. 따라서 실제 자료로 특허·시장 분석, 인용 검증, 통합 보고서, 화면과 다운로드까지 이어지는 출시 경로가 현재 환경에서 재현되었다고 확인되지 않았다.

이는 운영 서비스 전체가 중단되었다는 뜻이 아니다. 운영 배포 기록·실행 환경·승인된 실제 데이터에 접근해 확인한 결과가 없다는 뜻이다. 먼저 아래 게이트를 서비스 책임자가 확정하고, 각 항목에 로그·보고서·CI 실행·사람 평가 등 증거를 연결해야 한다.

| 게이트 | 현재 증거와 남은 확인 |
|---|---|
| 실제 데이터와 색인 | 로컬 특허 색인은 존재하나 현재 앱 설정은 공용 Chroma를 선택함. 공용 컬렉션 연결과 의도한 문서 범위를 확인해야 함. 로컬 시장 처리 데이터와 색인은 비어 있음 |
| 실제 분석 및 인용 | 코드에 특허·시장 보고서 스키마 및 일부 ID·문서 연결·원문 일치 검사가 있음. 실서비스 데이터로 각 보고서 상태와 인용 검증을 통과한 실행 기록은 확인되지 않음 |
| 근거 부족·오류·시간 초과 | `PartRun`의 `completed`, `no_results`, `error`, `skipped`, `timeout` 상태와 영역별 예외 격리가 코드에 있음. UI·다운로드까지 실제 부분 실패가 일관되게 보이는지는 시나리오별 확인이 필요함 |
| 주요 사용자 흐름 | Streamlit 화면과 통합 파이프라인이 구현되어 있음. 현재 연결 환경에서 입력부터 결과 저장·다운로드까지 이어지는 재현 실행은 확인하지 않음 |
| 검색 품질 기준선 | 시장 평가 데이터·결과 파일이 있음. 다만 실행 당시 데이터·설정·커밋과 현재 로컬 색인의 동일성이 이 조사만으로 보장되지 않음. 특허 후보는 70건 모두 미판정 |
| CI·배포·복구 | CI에 포맷, pytest, 자동화 스크립트, Docker 빌드, SCC 의존성 점검이 설정되어 있음. develop CI 성공 뒤 사람이 main 승격 PR을 병합하는 절차와 SCC 스모크 워크플로도 문서화되어 있음. 현재 브랜치의 CI, 실제 배포, 롤백 리허설은 확인하지 않음 |
| 보안·비용 | `.env`는 Git에서 제외되고 현재 준비 점검은 키 값 대신 설정 여부만 출력함. 검색 임베딩 API 비용은 자동 집계되지 않는다고 평가 문서가 밝힘. 운영별 비용 한도와 개인 정보 로그 점검은 별도 검증 필요 |

## 서비스 흐름 기준선

### 특허 RAG

| 단계 | 코드와 데이터 계약에서 확인한 동작 | 한계·운영 확인 |
|---|---|---|
| 입력·검색 계획 | `PatentSearchRequest`와 `StructuredIdea`; 기술 구성요소를 바탕으로 LLM이 한국어·영어 검색어 계획을 생성 |
| 수집·정제 | KIPRIS 서지·초록을 `PatentDocument`로 만들고 출원번호 중복을 제거. 선택 문헌은 별도 KIPRIS Plus 청구항 상세 API로 보강 |
| 청킹·메타데이터 | 초록 1개와 청구항별 1개 청크. 청구항 번호·독립/종속 유형·상위항·버전과 출원·공개 식별정보를 보존. 현재 수집·색인 계약은 초록과 청구항 중심이며 명세서 섹션·문단은 색인하지 않음 |
| 색인·검색 | Chroma + `text-embedding-3-small`; Dense가 기본이고 BM25 및 RRF Hybrid가 공통 엔진에 구현됨. RRF 상수 기본값은 60. 문헌 단위 중복 제거가 지원됨 |
| 후보 판정·근거 구성 | 검색 문헌을 LLM 관련성 판정으로 거르고, 후보가 부족하면 KIPRIS 검색을 보충. 선택 문헌별 청구항을 가져와 어휘 겹침을 기준으로 최대 5개 청구항을 고르고 가능한 상위항을 함께 선택 |
| 생성·인용 검사 | `PatentReport`/문헌별 비교 Pydantic 모델을 생성. 인용 ID 및 문헌 관계 검사와 인용 문구의 원문 포함 여부 검사가 있음. LLM 비교의 형식·ID 오류는 제한 재시도 |
| 주장 지지·통합 | 구성요소별 비교와 예비 신호가 생성되고 통합 보고서가 `P:` 근거를 보존함. 독립된 주장 단위 entailment/groundedness 검증은 확인되지 않음. 자동 비교는 법률 판단으로 취급하지 않는 경계가 문서·프롬프트에 있음 |
| 평가 | 고정 질의 5개, 후보 CSV 70건. 현재 후보는 검색 방식·순위가 가려진 상태이며 전부 미판정. 특허 지표는 아직 산출할 수 없음 |

특허 평가 기준은 최근 추가한 [특허 라벨링 가이드](../evaluation/patent_labeling.md)를 따른다. 실제 비교에서는 동일 질의·색인·후보 범위를 유지하고, 후보 수·reranker 차이는 별도 실험으로 다뤄야 한다.

### 시장 RAG

| 단계 | 코드와 데이터 계약에서 확인한 동작 | 한계·운영 확인 |
|---|---|---|
| 수집 | NAVER 뉴스 검색 API는 제목·요약·URL·발행일 중심. DART 사업보고서는 설정한 `사업의 내용` 섹션 본문을 추출 |
| 정제·청킹 | 뉴스는 동일 URL 병합 후 제목 유사도와 3일 창으로 중복 그룹화하며 제목+요약을 한 문서로 사용. DART는 표·이미지를 제외하고 섹션 본문을 문자 길이 기준으로 청킹 |
| 메타데이터·색인 | 출처 유형, URL, 발행/수집일, DART 보고 대상 연도·섹션, 관련 아이디어, 근거 성격을 저장. Chroma `news` 컬렉션에 OpenAI 임베딩과 함께 색인 |
| 검색·판정 | 5개 시장 차원별 질의. Dense/BM25/RRF Hybrid 지원. 뉴스와 DART를 별도 후보 수로 검색하고 중복 그룹을 제한. LLM 관련성 판정 및 근거 수·성격에 따른 충분성 판정 |
| 생성·검증 | `MarketReport`의 차원별 주장·인용·판정·한계 구조를 생성. ID·출처 및 수치 관련 규칙 검증과 제한된 재생성 흐름이 있음 |
| 평가 | 시장 사람 라벨 25문항 및 검색·답변 평가 산출물 파일이 존재함. 현재 시장 처리 JSONL 및 로컬 색인은 비어 있음. 기존 산출물의 데이터·커밋·설정과 현재 코드의 일치 여부는 재현 점검이 필요함 |

뉴스의 제목·요약은 원문 전체가 아니므로 이를 원문 근거로 표현하면 안 된다. DART 청킹은 표를 제외하므로 표에만 존재하는 매출 수치 등은 현재 색인만으로 검증할 수 없다. 수요 확인과 구매 신호 구분은 기존 시장 계약을 유지해야 한다.

### 공통 파이프라인·보고서·화면

- Streamlit은 `src.pipeline`을 호출하며, 파이프라인은 시장·특허를 병렬 실행하고 영역별 시간 제한과 상태를 결과에 기록한다. 한쪽 실패가 다른 쪽 결과를 지우지 않도록 분리되어 있다. 타임아웃 뒤 이미 전송된 외부 요청은 완료까지 남을 수 있다.
- `PipelineReport`는 특허·시장 보고서, 질문별 연결, 사업 검토, 경영진 요약, 실행 상태를 묶는다. 질문별 연결은 여섯 기준 중 하나라도 시장 또는 특허 근거가 연결되지 않으면 보류하도록 설계되어 있다.
- 보고서 Markdown·UI·내보내기 경로는 구현되어 있다. 부분 오류·타임아웃·미확인 상태가 화면·PDF·저장 기록에서 똑같이 표현되는지 실제 실행 확인이 필요하다.
- 구조화된 보고서는 인용 존재·연결·문구 정확성을 도울 수 있지만, 그 자체로 해당 인용이 주장을 논리적으로 지지함을 증명하지 않는다. 특허·시장 주장 단위 평가를 별도 품질 기준으로 둬야 한다.

## 운영·평가 기준선

| 항목 | 현재 상태 |
|---|---|
| 외부 의존성 | OpenAI(검색어·임베딩·판정·생성), KIPRIS Plus, NAVER 뉴스, DART, 선택적 공용 Chroma |
| 호출·비용 지점 | 질의 임베딩, LLM 검색어 계획, 관련성 판정, 보고서 생성, 질문 연결 등에 외부 호출 가능. 특허 검색 평가는 Dense/Hybrid 임베딩 호출 비용을 자동 집계하지 않음 |
| 오류·재시도 | 서비스별 오류 보고서와 영역별 실행 상태, 일부 제한 재시도 및 시간 제한이 코드에 있음. in-flight 호출 취소·전역 예산 제한은 확인되지 않음 |
| 재현 정보 | 평가 CSV에 검색 방식·모델·프롬프트 여부·커밋 등 일부 실행 정보가 기록됨. 모든 평가에 데이터셋·색인·질의·라벨 버전이 하나의 불변 실행 명세로 연결되는지는 추가 점검 필요 |
| 보안 | 비밀정보는 환경변수로 관리하고 `.env`는 Git 제외 상태임. 공용 Chroma는 HTTPS 및 개인 키 인증 문서가 있음. 사용자 아이디어·원문 로그 보관과 삭제 정책은 운영 기준으로 확인 필요 |
| CI·배포 | GitHub Actions가 코드 검사와 빌드를 수행하도록 구성됨. 배포는 main 승격 PR의 사람 병합 이후 진행하는 구조이며, 이 작업 브랜치에서 배포·CI 실행 결과를 확인하지 않음 |

## V1.0 이후 권장 작업 순서

V1.0 게이트가 승인되고 실제 경로가 재현되기 전에는 아래 항목을 제품 기능으로 확대하지 않는다. 게이트 통과 후 각 항목을 독립 평가한다.

1. 영역별 데이터 품질·색인 버전·원문 역추적 메타데이터 점검
2. 특허 청구항 문맥과 DART 섹션을 포함한 영역별 청킹 비교
3. 고정된 사람 라벨로 Dense·BM25·RRF 후보 수 실험
4. 검색 기준선 위에서 reranking 없음·Bi-Encoder·Cross-Encoder 비교
5. 중복·출처 다양성·청구항 부모 문맥·토큰 예산을 포함하는 Context Builder 평가
6. 인용 ID/소속/원문 일치와 주장 지지 여부를 별도 평가
7. UI·다운로드의 부분 결과·불확실성·출처 추적 흐름 검증
8. Multi-query, HyDE, Self-query, Query decomposition을 하나씩 비교하고 이득이 확인된 기법만 채택
9. 위 개선 후에도 반복되는 보고서 생성 오류가 사람 라벨 평가에서 남을 때 Fine-tuning 검토

각 실험은 API 호출 전 범위와 비용 영향을 확인하고, 질의별 결과·실패 예시·지연시간을 보존한다. 이 기준선에는 새로운 검색·생성 실험 결과가 포함되어 있지 않다.
